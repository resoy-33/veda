## 0. Conventions

- **Canonical JSON:** UTF-8, keys sorted, no extra whitespace, decimals as
  strings, timestamps as ISO-8601 UTC with `Z`. Hash = SHA-256 hex, lowercase.
- **Langue :** la couche métier (postes, ratios, libellés, UI, rapports, docs) est en
  **français** ; la plomberie technique (enveloppe HTTP/JSON, tables/colonnes SQL,
  identifiants Python) reste en anglais.
- **Amounts:** stored as decimal strings in **dinars** (no floats). Displayed in
  **MTND** (÷ 1,000,000, 3 decimals) to match the finance template.
- **IDs:** `filing_id` / `event_id` are UUIDv4 generated by the API. Hedera IDs
  are `0.0.<n>` strings.
- **Version:** every schema carries `"v": "1.0"`.
- **Idempotency:** `doc_sha256` is unique. Re-submitting the same PDF returns the
  existing filing.
- **Hedera limits:** HCS message ≤ 1024 bytes (chunk if needed); NFT metadata
  field ≤ 100 bytes → store the HFS **file ID** there; HFS `FileCreate` ≤ 4096 bytes.

## 1. HCS message schema

**One topic per filing.** Messages are appended in order; each carries the hash
of the previous message, forming a tamper-evident chain.

### 1.1 Envelope (every message)

```json
{
  "v": "1.0",
  "event_id": "3f2c...uuid",
  "filing_id": "9a71...uuid",
  "event": "filing_submitted | extracted | validated | sealed",
  "actor": "0.0.11060814",
  "role": "issuer | agent | verifier",
  "sector": "industrial",
  "ts": "2026-10-21T18:00:00Z",
  "prev_hash": "0000...0000",
  "payload": { }
}
```

- `prev_hash` = SHA-256 of the **canonical JSON of the previous message**.
  The genesis message uses 64 zeros.
- The message hash is **not stored**; readers recompute it from the canonical
  JSON (this avoids self-reference).
- `event_id` / `filing_id` are stable across the chain.

### 1.2 Payloads

**`filing_submitted`** (actor: issuer)
```json
{
  "issuer": "SAH",
  "period": "2025-12-31",
  "doc_sha256": "<hex64>",
  "mime": "application/pdf",
  "pages": 65,
  "source_url": null
}
```

**`extracted`** (actor: agent)
```json
{
  "extraction_sha256": "<hex64>",
  "model": "deterministic:pymupdf",
  "line_count": 42,
  "grounded_verified": 42,
  "grounded_total": 42
}
```

**`validated`** (actor: agent)
```json
{
  "extraction_sha256": "<hex64>",
  "ratios_sha256": "<hex64>",
  "verdict": "pass",
  "checks": [
    { "id": "assets_eq_liabilities", "status": "pass", "detail": "1452997177 = 1452997177" },
    { "id": "cashflow_tieout", "status": "pass", "detail": "68842302 - 15904215 = 52938087" }
  ]
}
```

**`sealed`** (actor: agent)
```json
{
  "report_sha256": "<hex64>",
  "credential": {
    "token_id": "0.0.11118143",
    "serial": 1,
    "metadata_file_id": "0.0.11118141"
  }
}
```

### 1.3 Event order (state machine)

```
filing_submitted → extracted → validated(pass|fail) → sealed
```

- On `fail`, write `validated{fail}` and **stop** (no `sealed`, no NFT).
- A filing is `verified` only if it reaches `sealed`.

## 2. NFT + HFS metadata schema

- HTS collection: **Verified Filing Credential** (non-fungible, finite supply).
- One serial per `(issuer, period)`.
- The NFT's metadata field (100-byte cap) contains the **HFS file ID** as bytes,
  e.g. `b"0.0.11118141"`.

HFS file contents (HIP-412-shaped, max 4096 bytes). `values` is the compact
line-item list (`k` key, `v` dinar value, `p` page, `c` confidence) used to
rehydrate the cache after a rebuild:

```json
{
  "name": "Dépôt vérifié — SAH 2025",
  "description": "États financiers vérifiés et scellés par l'agent d'intégrité.",
  "type": "application/json",
  "properties": {
    "issuer": "SAH",
    "period": "2025-12-31",
    "sector": "industrial",
    "doc_sha256": "<hex64>",
    "extraction_sha256": "<hex64>",
    "ratios_sha256": "<hex64>",
    "report_sha256": "<hex64>",
    "validation_verdict": "pass",
    "hcs_topic_id": "0.0.11118140",
    "hcs_sequence_range": [1, 4],
    "model": "deterministic:pymupdf",
    "created_at": "2026-10-21T18:02:00Z",
    "values": [
      { "k": "chiffre_affaires", "v": 983194664, "p": 3, "c": 0.95 }
    ]
  }
}
```

## 3. Verification algorithm (trustless)

Inputs: `topic_id`, `token_id`, `serial`.

1. `GET /api/v1/topics/{topic_id}/messages?order=asc&limit=100` (Mirror Node);
   base64-decode each `message`.
2. Parse and validate each envelope against §1.1.
3. Recompute the chain: first `prev_hash` = 64 zeros; for each `i > 0`,
   `prev_hash[i] == sha256(canonical_json(msg[i-1]))`.
4. Assert the event sequence and that every `filing_id` matches.
5. Assert `validated.verdict == "pass"` and that `sealed` exists.
6. `GET /api/v1/tokens/{token_id}/nfts/{serial}` → base64-decode metadata → file ID.
7. Fetch the HFS file (mirror files endpoint, or SDK `FileContentsQuery`) and parse.
8. Cross-check: `metadata.properties.doc_sha256` equals the `filing_submitted`
   payload; `extraction_sha256` and `report_sha256` equal the corresponding
   event payloads; `hcs_topic_id` matches; `hcs_sequence_range` covers the
   events. Messages larger than 1024 bytes are reassembled from their
   `chunk_info` before hashing.
9. Return `{ verified, checks[], evidence }`.

The verifier never trusts our database — only the Mirror Node + on-chain data.

## 4. API contract

Base: `/api/v1`. Auth: JWT (HS256), `Authorization: Bearer <token>`.

### 4.1 Auth
| method | path | body | result |
|---|---|---|---|
| POST | `/auth/login` | `{email, password}` | `{access_token, token_type:"bearer", expires_in, user}` |
| GET | `/auth/me` | — | `UserOut` |
| PATCH | `/auth/me` | `{display_name}` | `UserOut` |
| POST | `/auth/change-password` | `{current_password, new_password}` | `{status:"ok"}` |

`user = {id, email, role, hedera_account_id, display_name}`. `display_name` is
optional, 1–80 characters, and only affects presentation. Passwords are hashed
with PBKDF2-SHA256; changing a password keeps existing JWTs valid until expiry.

### 4.2 Filings
| method | path | role | result |
|---|---|---|---|
| POST | `/filings` | issuer | `202 {filing_id, status}` (multipart `file`) |
| POST | `/filings/{id}/extract` | issuer | `200 {filing_id, status, verdict, line_count, extraction_sha256, ratios_sha256, checks[]}` (multipart `file`, hash must match the filing) |
| POST | `/filings/{id}/seal` | issuer | `200 {filing_id, status, token_id, serial, metadata_file_id, report_sha256, hcs_sequence, hcs_sequence_range}` |
| GET | `/filings` | any | `{items:[FilingSummary], total}` |
| GET | `/filings/{id}` | any | `FilingDetail` (values, ratios, status) |
| GET | `/filings/{id}/timeline` | any | `{events:[Event]}` |
| GET | `/filings/{id}/credential` | any | `{token_id, serial, metadata_file_id, metadata}` |
| POST | `/filings/{id}/verify` | verifier | `{verified, checks[], evidence}` |
| GET | `/filings/{id}/report.xlsx` | any | `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` |
| POST | `/system/rebuild` | admin | `{rebuilt, filings, events}` |

`FilingSummary = {id, issuer, period, sector, status, doc_sha256, topic_id, token_id, serial, created_at}`

`topic_id` is nullable and identifies the filing's HCS topic, so clients can
link a filing to its proof without a second request.

`FilingDetail = FilingSummary + {unit, consolidation, values:[Value], ratios:[Ratio], timeline_count}`

`Value = {line_item, label_raw, value, page, snippet, unit, period, confidence}`

`Ratio = {code, name, year, value, formula_version}`

`Event = {sequence, event, actor, role, ts, hash, prev_hash, payload}`

### 4.3 Errors
```json
{ "error": { "code": "validation_failed", "message": "…", "details": {} } }
```
Codes: `unauthorized`, `forbidden`, `not_found`, `conflict`, `invalid_input`,
`validation_failed`, `hedera_error`, `internal_error`.

## 5. Database schema (rebuildable cache)

Every row must be derivable from the Mirror Node. `POST /system/rebuild` truncates
and replays the topics.

```sql
CREATE TABLE users (
  id UUID PRIMARY KEY,
  email TEXT UNIQUE NOT NULL,
  password_hash TEXT NOT NULL,
  role TEXT NOT NULL CHECK (role IN ('issuer','broker','verifier','admin')),
  hedera_account_id TEXT NOT NULL,
  display_name TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE filings (
  id UUID PRIMARY KEY,
  doc_sha256 TEXT UNIQUE NOT NULL,
  issuer TEXT NOT NULL,
  period DATE NOT NULL,
  sector TEXT NOT NULL,
  unit TEXT NOT NULL,
  consolidation TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('submitted','extracted','validated','sealed','failed')),
  topic_id TEXT,
  token_id TEXT,
  serial BIGINT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE values (
  id UUID PRIMARY KEY,
  filing_id UUID REFERENCES filings(id) ON DELETE CASCADE,
  line_item TEXT NOT NULL,
  label_raw TEXT NOT NULL,
  value NUMERIC(24,0) NOT NULL,
  page INT NOT NULL,
  snippet TEXT NOT NULL,
  unit TEXT NOT NULL,
  period TEXT NOT NULL,
  confidence NUMERIC(4,3) NOT NULL,
  bbox JSONB
);

CREATE TABLE ratios (
  id UUID PRIMARY KEY,
  filing_id UUID REFERENCES filings(id) ON DELETE CASCADE,
  code TEXT NOT NULL,
  name TEXT NOT NULL,
  year INT NOT NULL,
  value NUMERIC(18,6),
  formula_version TEXT NOT NULL
);

CREATE TABLE events (
  id UUID PRIMARY KEY,
  filing_id UUID REFERENCES filings(id) ON DELETE CASCADE,
  hcs_sequence BIGINT NOT NULL,
  event TEXT NOT NULL,
  actor TEXT NOT NULL,
  role TEXT NOT NULL,
  payload JSONB NOT NULL,
  prev_hash TEXT NOT NULL,
  hash TEXT NOT NULL,
  consensus_ts TIMESTAMPTZ
);

CREATE INDEX ON values(filing_id);
CREATE INDEX ON ratios(filing_id);
CREATE INDEX ON events(filing_id, hcs_sequence);
```

## 8. Moteur de ratios (déterministe)

Entrées : les postes ci-dessus, par exercice. Sorties :
`ratios(code, name, year, value, formula_version)`.

Familles (formula_version `1.0`) :
- **Agrégats :** postes calculés du §7.
- **Croissance :** variation annuelle du CA, de l'EBITDA, de l'EBIT, du résultat net,
  du BPA, du CFO, du DPA et du total actif.
- **Marges :** brute, EBITDA, exploitation, avant impôt, nette, FCF ; ratios de charges.
- **Rentabilité :** ROE, ROE sur capitaux moyens, ROA, ROA sur actif moyen, ROCE.
- **DuPont :** effet impôt, effet financier, marge d'exploitation, rotation de l'actif,
  levier financier.
- **Liquidité :** générale, réduite, réduite stricte, immédiate, immédiate élargie,
  couverture des passifs courants par le CFO.
- **Efficacité :** DIO, DSO, DPO, CCC ; rotations des stocks, créances, dettes.
- **Structure financière et couverture :** dettes/actif, autonomie financière, D/E,
  gearing, dette nette/EBITDA, couverture des intérêts (EBIT, EBITDA, EBITDA−Capex),
  CFO/dette brute.
- **Qualité des résultats :** FCF/RN, CFO/EBITDA, CFO/RN, Capex/CA, Capex/D&A, accruals.
- **Par action :** BPA, DPA, taux de distribution, VCPA, CFO/action, FCF/action.
- **Valorisation :** PER, rendement du bénéfice, P/B, P/S, P/CFO, P/FCF, valeur de Graham.

**Contrôles de cohérence** (reproduisent les lignes « Contrôle » du modèle ;
tolérance `max(1 dinar, 0,01 %)`) :
`actif_egal_passif`, `somme_actif`, `somme_passif`, `ebit_recalcule`,
`ebt_recalcule`, `resultat_net_recalcule`, `coherence_tresorerie`
(`tresorerie_cloture == liquidites − dettes_financieres_courantes`).
